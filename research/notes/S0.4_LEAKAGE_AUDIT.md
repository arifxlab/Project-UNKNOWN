# Project UNKNOWN

## S0.4 — Leakage Audit

**Project:** Project UNKNOWN — Autonomous Concept Formation & Model Discovery
**Sprint:** Sprint 0 — Research Foundation
**Stage:** S0.4 — Synthetic Environment Definition
**Artifact:** Leakage Audit
**Status:** Working Scientific Contract
**Date:** 2026-09-23

---

# 1. Purpose

This document defines the leakage controls required for the Project UNKNOWN synthetic environment.

The purpose is to ensure that the UNKNOWN discovery system can only use information that would legitimately be available to an agent operating through the public environment interface.

The central scientific requirement is:

> A successful representation discovery must arise from information available through the permitted observation and interaction interface, not from accidental access to hidden benchmark truth, task metadata, implementation details, evaluation labels, or artifacts that reveal the intended concept.

This audit therefore defines:

* what information is public;
* what information is hidden;
* what information is evaluation-only;
* what information may legitimately enter the discovery process;
* what information must never enter the discovery process;
* how leakage is detected;
* how leakage is tested;
* how leakage invalidates an experiment.

---

# 2. Scientific Principle

UNKNOWN is intended to investigate representation inadequacy.

Therefore the experiment must distinguish:

```text
Observable information
        ↓
Current representation
        ↓
Model / hypothesis
        ↓
Failure diagnosis
        ↓
Candidate representation
        ↓
Validation
```

from:

```text
Hidden benchmark truth
        ↓
Candidate representation
```

The second path is invalid.

If the system can directly access the answer, the resulting candidate cannot be interpreted as autonomous discovery.

---

# 3. Leakage Model

Leakage is defined as:

> Any information unavailable through the permitted public interaction interface that provides the discovery system with knowledge about hidden benchmark conditions, hidden state, intended representations, evaluation labels, or experiment outcomes.

Leakage may be:

* explicit;
* implicit;
* structural;
* statistical;
* metadata-based;
* temporal;
* serialization-based;
* implementation-based;
* logging-based;
* error-message-based;
* seed-based;
* filesystem-based;
* process-based.

The absence of an obvious hidden-state variable is therefore insufficient.

The experiment must be resistant to indirect information channels.

---

# 4. Information Classes

All experiment information is assigned to one of three classes.

## 4.1 PUBLIC

Public information is information legitimately available to UNKNOWN.

Examples:

* observations;
* observation history;
* permitted actions;
* permitted interventions;
* action results;
* observation timestamps if explicitly part of the public interface;
* public environment configuration;
* public task constraints;
* publicly documented API behavior;
* information returned by permitted tools;
* candidate-generation state derived from public information.

Public information may enter:

* representation construction;
* model fitting;
* failure diagnosis;
* candidate generation;
* candidate evaluation;
* experiment control logic available to UNKNOWN.

---

## 4.2 HIDDEN

Hidden information represents benchmark truth that must not be available to UNKNOWN.

Examples:

* hidden state variables;
* ground-truth latent structure;
* benchmark condition;
* intended missing variable;
* true causal relationships;
* hidden concept identity;
* hidden representation membership;
* oracle labels;
* evaluation-only annotations;
* hidden counterfactual outcomes;
* hidden transfer-task labels;
* benchmark construction parameters that directly reveal the target condition.

Hidden information may be used by the evaluation harness.

It must not be exposed to the discovery process.

---

## 4.3 EVALUATION-ONLY

Evaluation-only information is generated or derived specifically for assessing UNKNOWN.

Examples:

* ground-truth candidate identity;
* exact representation recovery labels;
* equivalent-representation mappings;
* hidden condition labels;
* post-hoc prediction scores;
* intervention accuracy;
* falsification outcomes;
* transfer scores;
* complexity comparisons;
* acceptance/rejection labels;
* benchmark-level aggregate statistics.

Evaluation-only information may be used after the discovery process produces an output.

It must not influence candidate construction or search.

---

# 5. Trust Boundary

The environment architecture must enforce the following boundary:

```text
                    ┌──────────────────────┐
                    │   Hidden Benchmark   │
                    │       Truth          │
                    └──────────┬───────────┘
                               │
                               │ evaluation only
                               ▼
                    ┌──────────────────────┐
                    │ Evaluation Harness   │
                    └──────────────────────┘


┌──────────────┐
│ Environment  │
│ Public API   │
└──────┬───────┘
       │
       │ observations / actions /
       │ interventions / public metadata
       ▼
┌──────────────────────┐
│ UNKNOWN Discovery    │
│ System               │
└──────────┬───────────┘
           │
           │ candidate representation
           │ hypotheses
           │ predictions
           ▼
┌──────────────────────┐
│ Evaluation Harness   │
└──────────────────────┘
```

The evaluation harness may know the hidden truth.

UNKNOWN may not.

The evaluation harness must not send hidden evaluation information back into the discovery process.

---

# 6. Public Interface Contract

UNKNOWN may interact with the environment only through the documented public interface.

The initial interface is:

```text
reset(config, seed)
observe()
step(action)
intervene(intervention)
is_terminal()
episode_metadata()
```

The implementation must not expose the underlying environment object directly.

UNKNOWN must not receive:

* internal object references;
* hidden-state objects;
* internal physics/dynamics objects;
* benchmark condition objects;
* ground-truth representation objects;
* evaluation objects;
* environment implementation modules.

---

# 7. Observation Leakage

Observations must contain only information intentionally available to the agent.

The following are prohibited unless explicitly defined as observable:

* hidden state values;
* hidden identifiers;
* target concept labels;
* benchmark condition labels;
* latent-variable names;
* ground-truth relation types;
* internal object IDs carrying semantic meaning;
* evaluation labels;
* oracle predictions;
* future states;
* future rewards;
* hidden causal structure.

An observation serializer must therefore be treated as a scientific boundary.

---

# 8. Identifier Leakage

Identifiers are a major potential leakage channel.

Identifiers must not encode hidden semantic information.

Invalid examples:

```text
missing_distance_entity
causal_condition_3
hidden_velocity_task
representation_failure_distance
target_concept_A
```

Valid examples:

```text
entity_0001
entity_0002
episode_0042
object_0007
```

Identifiers must be semantically meaningless.

Where necessary, identifiers should be generated independently of benchmark condition.

---

# 9. Configuration Leakage

Public configuration must not reveal hidden benchmark truth.

Invalid:

```text
representation_condition = "missing_distance"
```

Invalid:

```text
target_variable = "distance"
```

Invalid:

```text
benchmark_type = "representation_failure"
```

Potentially valid:

```text
world_size = 10
max_steps = 100
observation_mode = "standard"
```

The distinction is whether the configuration describes the public experimental interface or directly reveals the hidden condition being investigated.

---

# 10. Filename Leakage

Filesystem structure must not reveal benchmark truth.

Invalid:

```text
experiments/
    missing_distance/
    missing_velocity/
    missing_relation/
```

when UNKNOWN can inspect the filesystem.

Preferred:

```text
experiments/
    condition_001/
    condition_002/
    condition_003/
```

or opaque experiment identifiers.

If condition-specific organization is required internally, it must exist outside the discovery process's accessible filesystem.

---

# 11. Directory Leakage

UNKNOWN must not be given access to:

```text
evaluation/
hidden/
ground_truth/
oracle/
benchmark_truth/
```

or equivalent directories containing hidden information.

The runtime should use explicit dependency boundaries rather than relying solely on convention.

---

# 12. Import Leakage

UNKNOWN must not be able to import hidden benchmark modules.

For example, the discovery runtime must not have direct access to modules such as:

```text
environment.hidden
evaluation.oracle
benchmark.ground_truth
```

unless those modules contain only public functionality.

Where practical, the public runtime and evaluation runtime should have separate module boundaries.

---

# 13. Serialization Leakage

Serialized objects must be audited.

A public observation object must not contain hidden fields such as:

```text
hidden_state
ground_truth
target_variable
benchmark_condition
oracle_label
evaluation_score
```

even if those fields are ignored by UNKNOWN.

The principle is:

> Data that is physically available to the discovery process is potentially available information.

Therefore "we don't currently read it" is not sufficient.

---

# 14. Logging Leakage

Logs are part of the experimental interface whenever UNKNOWN can access them.

Logs must not contain hidden information.

Invalid:

```text
DEBUG: representation_failure=True
DEBUG: missing_variable=distance
DEBUG: ground_truth_relation=near
```

Potentially valid:

```text
DEBUG: observation received
DEBUG: model fit completed
DEBUG: validation failed
```

Logs accessible to UNKNOWN must therefore be generated from public information only.

---

# 15. Error Leakage

Error messages can reveal hidden information.

Invalid:

```text
Missing expected hidden variable: distance
```

Invalid:

```text
Benchmark condition does not contain velocity
```

Potentially valid:

```text
Invalid action format
```

Errors must describe interface failures rather than hidden benchmark truth.

---

# 16. Exception Leakage

Exceptions must not expose internal hidden objects or benchmark state.

The public runtime should translate internal exceptions into controlled public errors.

The evaluation harness may retain detailed internal diagnostics separately.

---

# 17. Seed Leakage

Random seeds must not encode benchmark conditions.

The following is prohibited:

```text
seed = 1 → condition A
seed = 2 → condition B
seed = 3 → condition C
```

if UNKNOWN can infer the condition from the seed.

Seeds must be treated as independent experimental controls.

Condition assignment should be independent of seed semantics.

---

# 18. Randomness Leakage

Random number generation must not produce systematic statistical signatures that reveal the hidden condition.

Potential leakage sources include:

* condition-specific random generators;
* different random distributions;
* different episode lengths;
* different object counts;
* different action spaces;
* different initialization distributions.

If these differences are scientifically intended, they must be part of the public environment definition.

If they are not intended, they must be controlled.

---

# 19. Episode-Length Leakage

Episode length can become an unintended label.

Example:

```text
Condition A → always 50 steps
Condition B → always 100 steps
```

If UNKNOWN can identify the condition from episode length, the benchmark is contaminated.

Episode-length distributions should therefore be matched or explicitly justified.

---

# 20. Observation-Count Leakage

The number of observations or interactions required before termination must not unintentionally reveal the hidden condition.

Where possible:

* maximum horizons should be standardized;
* termination rules should be matched;
* failed episodes should not expose hidden labels;
* discovery and evaluation conditions should use comparable interaction budgets.

---

# 21. Timing Leakage

Execution time can become an information channel.

Potential sources include:

* condition-specific computation;
* hidden-state calculation;
* different model branches;
* benchmark-specific preprocessing.

Timing should not systematically encode the hidden condition.

Where exact timing control is impractical, timing must not be exposed as a discovery signal.

---

# 22. Metadata Leakage

Metadata is considered public only if it is intentionally part of the public environment contract.

Potentially dangerous metadata includes:

* benchmark name;
* condition name;
* target concept;
* representation family;
* hidden-state dimensionality;
* number of hidden variables;
* ground-truth feature count;
* benchmark generation method;
* evaluation labels.

Safe metadata should be limited to information required for legitimate interaction.

---

# 23. Ground-Truth Leakage

Ground truth must remain outside the discovery path.

The following may exist internally:

```text
GroundTruthRepresentation
GroundTruthCausalGraph
GroundTruthConcept
GroundTruthCondition
GroundTruthState
```

but they must only be accessible to the evaluation harness.

The discovery system must never request these objects.

---

# 24. Future-State Leakage

The environment must not expose future state information.

UNKNOWN may receive:

```text
current observation
```

but not:

```text
future observation
future hidden state
future reward
future transition
```

unless the task explicitly defines such information as observable.

---

# 25. Counterfactual Leakage

Counterfactual information is especially sensitive.

If UNKNOWN is being evaluated on intervention outcomes, it must generate the intervention itself through the permitted interface.

The environment must not provide oracle counterfactual answers.

Invalid:

```text
predict_intervention(intervention)
→ ground_truth_counterfactual
```

when the method is supposed to discover the intervention effect itself.

Valid:

```text
UNKNOWN predicts intervention outcome
        ↓
environment executes intervention
        ↓
observed outcome
        ↓
evaluation compares prediction with outcome
```

---

# 26. Transfer Leakage

Transfer tasks must remain hidden until the appropriate evaluation phase.

UNKNOWN must not receive:

* transfer-task labels;
* target concept identity;
* hidden context labels;
* ground-truth transfer mapping.

The system may receive the public interface for the new environment/context.

The transfer evaluation determines whether the candidate representation remains useful outside the discovery context.

---

# 27. Candidate Leakage

Candidate generation must not use evaluation results from future tests.

The system must not generate candidates using:

```text
future intervention score
future transfer score
ground-truth recovery score
evaluation-only acceptance label
```

before those evaluations are formally conducted.

Otherwise the validation set becomes part of training/search.

---

# 28. Test-Set Leakage

Evaluation data must be separated from discovery data.

At minimum:

```text
Discovery
    ↓
Candidate generation
    ↓
Frozen validation
    ↓
Final evaluation
```

The final evaluation must not be used to repeatedly modify the candidate.

If repeated optimization against the final evaluation occurs, the result is no longer a clean final evaluation.

---

# 29. Benchmark-Construction Leakage

Benchmark generation itself must be audited.

A benchmark can leak even when the runtime interface appears clean.

Potential sources:

* condition-specific distributions;
* unique object counts;
* unique trajectory patterns;
* unique noise levels;
* unique episode lengths;
* unique action availability;
* unique initialization;
* unique rendering;
* unique observation statistics.

The benchmark must therefore be tested for distinguishability.

---

# 30. Condition-Indistinguishability Test

For paired conditions, public observations should be statistically controlled whenever the hidden condition is not intended to be directly observable.

The test should examine:

* observation distributions;
* episode lengths;
* object counts;
* action availability;
* transition statistics;
* timing;
* metadata;
* identifiers;
* initialization;
* termination behavior.

If a classifier can identify the hidden benchmark condition directly from public metadata or superficial statistics, the benchmark requires investigation.

---

# 31. Paired Counterfactual Requirement

The core benchmark should include paired conditions that differ in one scientifically controlled property.

Example:

```text
PAIR A

Condition A:
Relevant distinction absent from R.

Condition B:
Same observable setup,
but relevant distinction retained in R.
```

The purpose is to test whether UNKNOWN can distinguish:

```text
representation limitation
```

from:

```text
model-family limitation
```

without being given the answer.

---

# 32. Information-Unavailable Control

A separate condition must test the case where the relevant information is genuinely absent from the observation interface.

Expected behavior:

```text
Observation interface lacks required information
        ↓
No valid representation extension can recover it
        ↓
UNKNOWN should not claim successful discovery
```

This is a critical negative control.

---

# 33. Decoy Condition

The benchmark should contain cases where an apparently useful candidate improves prediction but does not represent the underlying reusable distinction.

Example:

```text
Candidate:
correlated surface feature

True mechanism:
different latent relation
```

The candidate may perform well on discovery data but fail:

* intervention;
* falsification;
* transfer.

This prevents predictive correlation from being treated as concept discovery.

---

# 34. Model-Family Control

A stronger model-family baseline must be evaluated.

If a stronger model succeeds using the existing representation, then the failure must not be classified as representation failure.

Expected diagnostic pattern:

```text
Current representation
        │
        ├── weak model fails
        │
        └── stronger model succeeds
                ↓
        model-family limitation
```

The benchmark must therefore prevent UNKNOWN from labeling every predictive failure as representation failure.

---

# 35. Parameter Control

Parameter optimization must be attempted before declaring representation failure where scientifically appropriate.

Expected pattern:

```text
Current representation
        │
        ├── parameter optimization fails
        ├── stronger model family fails
        └── representation extension succeeds
```

Only then does the representation-failure hypothesis become supported.

---

# 36. Feature-Engineering Control

Conventional feature engineering must be included as a comparison where appropriate.

The purpose is not to prohibit feature engineering.

The purpose is to determine whether UNKNOWN provides a distinct scientific capability beyond ordinary feature construction.

---

# 37. Always-On Search Control

A required ablation is:

```text
UNKNOWN:
search for representation extensions only after diagnosing failure

versus

Always-On:
search for representation extensions regardless of failure
```

The benchmark should determine whether failure-triggered search provides measurable scientific value.

Possible measurements include:

* unnecessary search frequency;
* search cost;
* candidate count;
* false discovery rate;
* generalization;
* transfer performance;
* computational budget;
* intervention validity.

No predetermined winner should be assumed.

---

# 38. Filesystem Audit

The discovery runtime must be tested against filesystem access.

Required checks:

* hidden directories inaccessible;
* evaluation files inaccessible;
* ground-truth files inaccessible;
* condition-specific filenames unavailable;
* benchmark source files unavailable;
* hidden configuration unavailable.

The test should be automated where practical.

---

# 39. Import Audit

The discovery runtime should be checked for prohibited imports.

Examples:

```text
evaluation.oracle
environment.hidden
benchmark.ground_truth
```

The exact implementation mechanism may vary, but the scientific invariant remains:

> UNKNOWN must not have programmatic access to hidden truth.

---

# 40. Object-Graph Audit

A public object must not indirectly reference hidden objects.

For example:

```text
PublicEnvironment
    └── hidden_state
```

is unsafe even if no public method explicitly exposes `hidden_state`.

The public runtime object graph must therefore be audited.

---

# 41. Serialization Audit

For every public schema:

1. serialize;
2. inspect serialized representation;
3. recursively inspect nested structures;
4. verify absence of hidden fields;
5. verify absence of hidden references;
6. verify identifier neutrality.

This should become an automated test.

---

# 42. Logging Audit

Every log channel accessible to UNKNOWN must be audited.

The audit should classify logs as:

```text
PUBLIC-SAFE
EVALUATION-ONLY
FORBIDDEN
```

Evaluation logs may contain hidden truth.

Discovery logs may not.

---

# 43. Reproducibility vs Leakage

Reproducibility requires sufficient information to recreate an experiment.

However:

> Reproducibility does not justify exposing hidden benchmark truth to the discovery process.

Therefore experiment manifests must distinguish:

```text
public reproducibility information
```

from:

```text
evaluation-only reproducibility information
```

A complete external experiment record may contain both, while the UNKNOWN runtime receives only the public subset.

---

# 44. Public Experiment Manifest

The public manifest may contain:

* experiment identifier;
* public environment version;
* public schema version;
* random seed;
* public action configuration;
* public observation configuration;
* interaction budget;
* software version;
* dependency version;
* reproducibility information that does not reveal hidden truth.

It must not contain:

* hidden condition;
* target concept;
* ground-truth representation;
* oracle labels;
* evaluation scores.

---

# 45. Hidden Evaluation Manifest

The evaluation manifest may contain:

* benchmark condition;
* hidden state configuration;
* ground-truth representation;
* equivalent representations;
* target concept;
* expected intervention effects;
* transfer ground truth;
* evaluation thresholds.

This manifest must remain outside the discovery runtime.

---

# 46. Candidate Provenance

Every candidate representation must record provenance.

Required provenance fields should include:

* candidate identifier;
* source observations;
* source representation;
* triggering failure evidence;
* generation method;
* search constraints;
* candidate expression;
* dependencies;
* creation timestamp or experiment step;
* evaluation status.

Provenance must not include hidden ground truth.

---

# 47. Failure-Diagnosis Leakage

Failure diagnosis is itself vulnerable to leakage.

UNKNOWN must infer failure from evidence available through the public evaluation protocol.

The system must not receive:

```text
failure_type = REPRESENTATION_FAILURE
```

from the benchmark.

Instead it must produce a diagnosis:

```text
UNKNOWN diagnosis:
REPRESENTATION_FAILURE
```

and the evaluation harness may later compare that diagnosis against hidden truth.

---

# 48. Acceptance Leakage

Candidate acceptance must not be driven by hidden labels.

The candidate-selection mechanism must operate using the frozen protocol.

The evaluation harness may determine whether the final candidate satisfies the scientific acceptance criteria.

---

# 49. Human Leakage

During automated experiments, human intervention can also contaminate results.

Researchers must not manually tell UNKNOWN:

* which variable is missing;
* which representation to search;
* which candidate is correct;
* which benchmark condition is active;
* which intervention will succeed.

Human intervention should be documented if it occurs.

If manual guidance affects the discovery process, that run must be classified accordingly.

---

# 50. External Model Leakage

If an external or pretrained model is used, its information sources must be documented.

Potential concerns include:

* benchmark data in pretraining;
* task-specific supervision;
* hidden labels;
* external APIs;
* retrieved documents containing benchmark answers;
* tool calls that reveal hidden state.

External models must therefore be treated as part of the information boundary.

A model cannot be assumed to be "publicly informed" merely because it is externally available.

---

# 51. Tool Leakage

Tools available to UNKNOWN must be explicitly enumerated.

Each tool must have:

* name;
* purpose;
* input schema;
* output schema;
* public information class;
* prohibited information;
* logging behavior;
* error behavior.

A tool is considered part of the agent's observation interface.

---

# 52. Network Leakage

The discovery runtime should not have unrestricted network access unless network access is explicitly part of the experiment.

Otherwise UNKNOWN could potentially retrieve:

* benchmark documentation;
* hidden source code;
* evaluation labels;
* generated benchmark descriptions;
* external answers.

Default research configuration:

```text
Network access: disabled
```

If network access becomes experimentally necessary, it must be documented and audited.

---

# 53. Environment-Variable Leakage

Environment variables are potential hidden channels.

UNKNOWN must not inherit variables containing:

```text
GROUND_TRUTH
BENCHMARK_CONDITION
TARGET_CONCEPT
EVALUATION_RESULT
ORACLE
HIDDEN_STATE
```

or equivalent information.

The discovery process should receive a controlled environment.

---

# 54. Process-Argument Leakage

Command-line arguments can leak benchmark information.

Invalid:

```text
python discover.py --missing-variable=distance
```

Potentially valid:

```text
python discover.py --experiment-id=exp_0042
```

provided the identifier carries no hidden semantic information.

---

# 55. Environment-Variable and Process Audit

Before each experiment, the discovery runtime should be checked for:

* environment variables;
* command-line arguments;
* mounted directories;
* accessible files;
* network interfaces;
* inherited processes;
* exposed ports;
* shared memory;
* temporary files.

The experiment should fail closed if hidden information is accessible.

---

# 56. Container Boundary

Where practical, UNKNOWN should execute in an isolated runtime.

Recommended boundary:

```text
Host
 │
 ├── Evaluation Harness
 │
 └── UNKNOWN Runtime
       │
       ├── Public API
       ├── Public data
       └── Discovery state
```

The UNKNOWN runtime should not mount evaluation directories.

Containerization is an engineering control, not a substitute for scientific auditing.

---

# 57. Hidden-State Access Test

A negative test must attempt to access hidden state through the public environment.

Expected result:

```text
access denied
```

or:

```text
hidden state unavailable
```

No hidden object should be returned.

---

# 58. Ground-Truth Access Test

A negative test must attempt to request ground-truth representation data.

Expected result:

```text
access denied
```

The test passes only if the discovery runtime cannot obtain the ground truth.

---

# 59. Evaluation-Score Access Test

UNKNOWN must not receive its own evaluation score during discovery unless that score is explicitly part of the permitted search protocol.

In the core experiment:

```text
candidate generation
        ↓
frozen evaluation
```

not:

```text
candidate generation
        ↓
evaluation score
        ↓
candidate modification
        ↓
evaluation score
        ↓
...
```

when the score comes from the final held-out evaluation.

---

# 60. Hidden Condition Classifier Audit

An auxiliary classifier may be trained to determine whether public data accidentally reveals the hidden condition.

Input sources may include:

* metadata;
* identifiers;
* observations;
* episode statistics;
* timing;
* action traces.

If a hidden condition is trivially recoverable from unintended channels, the benchmark must be investigated.

A recoverable condition is not automatically invalid if the condition is intentionally observable.

The key question is whether the signal represents the intended scientific variable or an accidental shortcut.

---

# 61. Shortcut Audit

Every benchmark condition must be checked for unintended shortcuts.

Examples:

```text
target concept = distance
but object color also uniquely identifies condition
```

or:

```text
target concept = relation
but episode length uniquely identifies condition
```

Such shortcuts undermine interpretation.

The benchmark should minimize accidental correlations between:

```text
hidden condition
```

and:

```text
irrelevant public variables
```

---

# 62. Representation Audit

The current representation must be explicitly defined.

For each benchmark:

```text
R(o_history)
```

must specify exactly which information is retained.

The audit must verify that:

1. required information is present in the observation interface;
2. the current representation excludes the intended distinction;
3. the distinction can be expressed by the permitted extension language;
4. stronger model families cannot recover it from the existing representation.

Only then can a representation-failure condition be supported.

---

# 63. Information-Availability Audit

For every intended representation failure:

```text
Observation
    ↓
Does required information exist?
```

If:

```text
NO
```

the condition is:

```text
INFORMATION_UNAVAILABLE
```

not:

```text
REPRESENTATION_FAILURE
```

If:

```text
YES
```

continue.

Then test:

```text
Current representation
    ↓
Does required distinction survive?
```

If:

```text
NO
```

a representation limitation may exist.

---

# 64. Model-Family Audit

For every apparent representation failure:

```text
Current representation
        ↓
Model family M1
        ↓
failure
```

must be followed by investigation of stronger model families where applicable.

If:

```text
Current representation
        ↓
Stronger model family
        ↓
success
```

the failure should be attributed to model-family limitations rather than representation inadequacy.

---

# 65. Parameter Audit

Similarly:

```text
Current representation
        ↓
parameter optimization
        ↓
success/failure
```

must be recorded.

Poor parameterization must not be mistaken for representation failure.

---

# 66. Representation-Extension Audit

A candidate extension must be evaluated for:

* information source;
* computability;
* provenance;
* complexity;
* novelty relative to current representation;
* predictive value;
* intervention value;
* falsification behavior;
* transfer behavior.

A candidate that merely memorizes training examples is insufficient.

---

# 67. Candidate Information Source

The candidate must be computable from permitted information.

Formally:

```text
C = f(public_information)
```

not:

```text
C = f(hidden_ground_truth)
```

The implementation should preserve enough provenance to establish this.

---

# 68. Candidate Search Constraints

The search language must be fixed before final evaluation.

The experiment must document:

* candidate grammar;
* maximum complexity;
* available primitive operations;
* maximum search depth;
* search budget;
* model family;
* optimization budget.

Changing these after seeing final evaluation results constitutes a protocol change and must be recorded.

---

# 69. Complexity Leakage

The benchmark must not reward candidates simply because they encode hidden truth through excessive complexity.

Candidate complexity must therefore be measured.

Potential controls include:

* expression size;
* number of primitive operations;
* parameter count;
* description length;
* search cost;
* reusable-state dimension.

The exact metric is an experimental choice and must be frozen before final evaluation.

---

# 70. Falsification Leakage

Falsification tests must be generated independently of the candidate where possible.

A candidate must not be allowed to define its own evaluation in a way that makes falsification impossible.

Required distinction:

```text
candidate proposes hypothesis
        ↓
independent evaluation tests hypothesis
```

not:

```text
candidate proposes hypothesis
        ↓
candidate chooses test that confirms hypothesis
```

---

# 71. Intervention Leakage

Interventions must be generated independently of hidden truth.

The intervention suite should be specified by the benchmark protocol.

UNKNOWN predicts outcomes.

The environment then executes the intervention.

The observed outcome is compared against the prediction.

---

# 72. Transfer Leakage

Transfer contexts must be selected without revealing the hidden target concept.

The candidate should be evaluated in contexts where superficial correlations can break.

A candidate that succeeds only because a training-context correlation remains unchanged should not receive strong transfer evidence.

---

# 73. Temporal Leakage

Discovery runs must not access future experiment results.

The system must not inspect:

* future episode logs;
* future candidate evaluations;
* later benchmark runs;
* final evaluation artifacts.

Experiment ordering should be controlled.

---

# 74. Cross-Run Leakage

Separate experiment runs must not share hidden state through:

* cached files;
* temporary files;
* databases;
* process memory;
* model checkpoints;
* logs;
* environment variables.

Each run should have an explicit isolation policy.

---

# 75. Cache Leakage

Caches can unintentionally reveal prior results.

Potential examples:

```text
~/.cache/
results/
tmp/
model_cache/
```

If UNKNOWN can access cached benchmark-specific artifacts, the experiment may be contaminated.

Caches should be isolated or disabled.

---

# 76. Checkpoint Leakage

Model checkpoints generated during evaluation must not be made available to the discovery process if they contain information derived from hidden evaluation data.

Training/discovery checkpoints and evaluation artifacts must remain separate.

---

# 77. Database Leakage

If a database is used, UNKNOWN must receive only the permitted public schema.

The database should enforce access control at the data layer where practical.

Hidden evaluation tables must not be queryable.

---

# 78. API Leakage

If the environment is exposed through an API, endpoints must be separated into:

```text
PUBLIC
```

and:

```text
EVALUATION
```

UNKNOWN should have credentials or routing that permit only public endpoints.

The evaluation service must use separate authorization.

---

# 79. Audit Logging

The system should record access attempts to sensitive interfaces.

Useful audit events include:

* hidden-state access attempt;
* evaluation endpoint access attempt;
* forbidden filesystem access;
* forbidden import;
* network access;
* hidden-variable request;
* evaluation-score request.

These logs belong to the evaluation layer and must not become discovery inputs.

---

# 80. Fail-Closed Principle

If the system cannot determine whether an information channel is public or hidden, it should be treated as restricted until audited.

The default is:

```text
unknown information
        ↓
not permitted
```

This prevents ambiguous channels from becoming accidental scientific shortcuts.

---

# 81. Leakage Severity

Leakage should be classified.

## Level 0 — No leakage

No hidden information is available.

Experiment remains valid.

## Level 1 — Benign engineering artifact

A non-semantic implementation artifact exists but does not provide useful hidden information.

Must still be documented.

## Level 2 — Potential shortcut

A public signal correlates with hidden condition.

Requires investigation.

## Level 3 — Material leakage

UNKNOWN can infer hidden benchmark information through an unintended channel.

Run should not be used as primary evidence.

## Level 4 — Direct oracle access

UNKNOWN receives ground truth or equivalent evaluation information.

Run is invalid for autonomous discovery claims.

---

# 82. Run Validity

Each experiment run should have a leakage status:

```text
VALID
QUESTIONABLE
INVALID
```

Suggested interpretation:

### VALID

No material leakage identified.

### QUESTIONABLE

Potential leakage exists but its scientific effect requires analysis.

### INVALID

Hidden information materially entered the discovery process.

Invalid runs may be retained for debugging but must not support the primary scientific claim.

# 89. Failure Conditions

S0.4 must be considered failed if:

* UNKNOWN receives ground-truth representation data;
* UNKNOWN receives hidden condition labels;
* UNKNOWN receives evaluation labels during discovery;
* hidden state becomes accessible through the public API;
* hidden state appears in public serialization;
* hidden truth is encoded in identifiers;
* hidden truth is encoded in configuration;
* hidden truth is encoded in filenames accessible to UNKNOWN;
* hidden truth is exposed through logs or errors;
* final evaluation results are repeatedly fed into candidate search;
* information-unavailable conditions are incorrectly treated as representation failures;
* model-family failures are incorrectly treated as representation failures because stronger baselines were not tested;
* benchmark shortcuts make the hidden condition trivially identifiable through unintended channels.

# 90. Scientific Interpretation Rule

A clean experiment does not mean that UNKNOWN has discovered a concept.

It means only that:

> The experiment provides a controlled information boundary within which autonomous discovery can be meaningfully evaluated.

Discovery requires additional evidence.

In particular, a candidate must survive the full validation protocol:

```text
representation inadequacy
        ↓
candidate generation
        ↓
prediction
        ↓
intervention
        ↓
falsification
        ↓
transfer
        ↓
complexity/provenance checks
        ↓
scientific acceptance or rejection
```

Leakage control protects the interpretation of every step.



versus:


A valid benchmark must make these experimentally distinguishable without exposing the correct diagnosis.

This distinction is one of the core scientific requirements of Project UNKNOWN.

# 92. Relation to Candidate Discovery

The candidate representation must be derived only from permitted information.

Therefore:

```text
Candidate = f(public observations,
              public actions,
              public interventions,
              public history,
              permitted computation)
```

and never:

```text
Candidate = f(hidden state,
              ground truth,
              evaluation labels)
```

This is a hard invariant.

---

# 93. Relation to Reproducibility

Every valid run should be reproducible without violating the information boundary.

A researcher must be able to reconstruct:

* environment version;
* public configuration;
* seed;
* software version;
* discovery configuration;
* evaluation protocol;
* leakage audit result.

However, the discovery runtime must receive only the public subset.

# 94. Relation to Scientific Claims

Leakage status must be attached to every result.

No result from an invalid run may be used as evidence for:

* representation failure detection;
* autonomous concept discovery;
* intervention validation;
* falsification;
* transfer;
* generalization;
* superiority over baselines;
* research contribution claims.

Invalid results may remain useful for debugging.

They are not scientific evidence.

# 95. Final S0.4 Leakage Contract

Project UNKNOWN adopts the following contract:

> UNKNOWN may use only information explicitly available through the permitted public environment and tool interfaces. Hidden benchmark truth, evaluation-only information, implementation internals, and unintended metadata channels must remain inaccessible to the discovery process. Every material information path must be audited statically and dynamically. Any run in which hidden information materially influences discovery is invalid as evidence for autonomous representation discovery.

This contract is binding for subsequent implementation and experimentation.
