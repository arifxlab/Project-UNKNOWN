# S0.5-D.5.3.3 — M1 Model-Family Failure Construction

## Status

**Research/design contract — ready for closure**

This document defines the controlled construction of **M1 Model-Family Failure** conditions for Project UNKNOWN.

M1 is a controlled failure class in which:

- the baseline representation `R₀` is sufficient;
- the selected baseline model family `M₀` is insufficient;
- parameter revision within `M₀` cannot recover the true mapping;
- a predefined richer model family `M₁` can recover the mapping;
- `M₁` operates over the unchanged `R₀`;
- the target mapping is identifiable under the permitted public experimental protocol.

M1 is therefore a **mapping-class failure**, not a representation failure.

---

## 1. Objective

The objective of D.5.3.3 is to define a scientifically controlled benchmark condition in which predictive failure is caused by an insufficient model family while the available representation already contains the information required to predict the target.

The benchmark must allow UNKNOWN to distinguish:

```text
P1 — parameter failure
M1 — model-family failure
R1 — representation-level inadequacy
N1 — non-identifiability / insufficient evidence
X1 — stochastic variation
```

The central question is:

> Can UNKNOWN determine that its current model family is inadequate without incorrectly attributing the failure to parameters or representation?

---

## 2. Scientific Boundary

The canonical distinction is:

**P1:**
```
R₀ sufficient
M₀ sufficient
θ₀ incorrect
→ parameter revision is sufficient
```

**M1:**
```
R₀ sufficient
M₀ insufficient
M₁ sufficient
→ model-family revision is sufficient
```

**R1:**
```
R₀ insufficient
M₀ insufficient
M₁ insufficient
R₁ sufficient
→ representation extension is required
```

The distinctions are structural.

**Prediction improvement alone does not define any failure class.**

---

## 3. Core Objects

Let:

- `H` = public history
- `R₀(H)` = baseline representation
- `M₀` = baseline model family
- `M₁` = predefined richer model family
- `θ` = model parameters
- `Y` = target outcome
- `f*` = true public mapping

Baseline prediction:

```
Ŷ = M₀(R₀(H); θ)
```

The true environment mapping is:

```
Y = f*(H)
```

The M1 condition requires:

```
f* ∉ Closure(M₀, R₀)
```

while:

```
f* ∈ Closure(M₁, R₀)
```

The representation remains unchanged.

---

## 4. Model-Family Definition

A model family is a formally specified class of admissible mappings from a fixed representation to target outcomes.

Model-family identity is determined by its **mapping class** rather than:

- model name;
- software library;
- implementation language;
- parameter count;
- model size;
- optimization algorithm;
- training performance.

A model family must define:

- input contract;
- output contract;
- mapping grammar;
- parameter domains;
- composition rules;
- resource constraints;
- admissible operations.

The family must be frozen before final UNKNOWN evaluation.

---

## 5. Model-Family Closure

For representation `R₀` and model family `M`, define:

```
Closure(M, R₀)
```

as the set of mappings from valid `R₀` representations to valid outputs that can be produced by the frozen model-family grammar under its declared parameter, composition, and resource constraints.

The benchmark uses closure to distinguish parameter failure from model-family failure.

**P1**
```
f* ∈ Closure(M₀, R₀)
```
but the current parameterization is incorrect.

**M1**
```
f* ∉ Closure(M₀, R₀)
f* ∈ Closure(M₁, R₀)
```

**R1**
```
f* ∉ Closure(M₀, R₀)
f* ∉ Closure(M₁, R₀)
f* ∈ Closure(M₁, R₁)
```

The closure distinction is conceptual ground truth and must not be inferred solely from empirical performance.

---

## 6. Expressibility Is Not Performance

The benchmark must **not** define M1 as:

> M1 performs better than M0.

A model may fail empirically even when the required mapping is expressible because of:

- poor initialization;
- insufficient optimization;
- insufficient data;
- numerical instability;
- implementation defects;
- premature stopping;
- practical estimation difficulty.

Therefore:

> **Empirical failure is evidence; structural expressibility determines the benchmark condition.**

Canonical M1 conditions should have an evaluator-verifiable expressibility boundary.

---

## 7. Constructive Expressibility Witness

Where possible, each M1 condition should contain a constructive witness.

A witness contains:

```
M1Witness
├── baseline representation R₀
├── target mapping f*
├── baseline family M₀
├── expanded family M₁
├── evidence that f* ∉ F₀
├── evidence that f* ∈ F₁
└── held-out validation evidence
```

For finite benchmark domains, the evaluator may construct a witness set:

```
D = {(r₁,y₁), ..., (rₙ,yₙ)}
```

such that:

- there is no `f ∈ F₀` satisfying all pairs

while:

- there exists `f ∈ F₁` satisfying all pairs

This provides executable evidence without requiring unrestricted mathematical function equivalence.

---

## 8. Finite-Domain Qualification

Expressibility is always evaluated relative to a declared experimental domain where necessary.

Let:

```
D_protocol
```

be the set of valid public representations that the permitted experimental protocol can generate.

Then an M1 condition may be defined as:

```
f*|D_protocol ∉ F₀|D_protocol
```

and:

```
f*|D_protocol ∈ F₁|D_protocol
```

This prevents accidental claims about inputs that the benchmark can never expose.

The protocol must be sufficiently rich to prevent the target mapping from collapsing into a simpler mapping class.

---

## 9. Baseline Representation Invariant

M1 requires:

```
R₀(M₀) == R₀(M₁)
```

The richer model family must consume exactly the same representation contract.

A model-family expansion may change **how** existing information is mapped to outcomes.

It may **not** introduce new representational information.

---

## 10. Forbidden Model-Family Bypass

An M1 implementation may not access raw observations that were excluded from `R₀`.

**Forbidden:**

```
Public observation
       ├──────────────→ M₁
       └→ R₀
```

**Required:**

```
Public observation
       ↓
R₀ construction
       ↓
M₀ / M₁
```

M1 must not access:

- hidden state;
- evaluator truth;
- condition labels;
- raw observations outside R₀;
- newly invented primitives;
- newly introduced relations;
- unbounded temporal history.

Otherwise the experiment is no longer a pure model-family comparison.

---

## 11. Parameter Boundary

Parameter changes and model-family changes must remain separate.

**Parameter revision** — same mapping class, different `θ`

**Model-family revision** — different mapping class, same representation

Example:

`M₀`:
```
y = ax + b
```

Changing:
```
a = 1 → a = 2
```
is **P1**.

Changing the admissible family to:

`M₁`:
```
y = ax² + bx + c
```
is **M1**.

The new structural term belongs to the mapping family, not the old parameter vocabulary.

---

## 12. Canonical World Family

The canonical M1 world family is:

> **Typed Functional Dynamics**

The public transition has the form:

```
x[t+1] = F*(x[t], u[t])
```

where:

- `x[t]` is publicly observable state;
- `u[t]` is publicly observable action/control;
- `x[t+1]` is publicly observable outcome;
- `F*` is private evaluator truth.

The canonical world is deterministic and initially noise-free.

---

## 13. Canonical Representation

The initial scalar representation may contain:

```
R₀(t) =
{
    state,
    action,
    previous_state,
    step_index
}
```

The exact representation contract remains governed by D.5.1.

No condition metadata or evaluator diagnosis is included.

---

## 14. Canonical M0

The initial baseline family is:

> `M₀` = bounded affine transition family

For a scalar state:

```
x[t+1] = a·x[t] + b·u[t] + c
```

For vector states:

```
x[t+1] = A x[t] + B u[t] + c
```

Parameter domains are explicitly bounded and frozen.

---

## 15. Canonical M1

The first richer family is:

> `M₁` = bounded interaction / quadratic family

For example:

```
x[t+1]
    = a·x[t]
    + b·u[t]
    + c·x[t]u[t]
    + d
```

The representation remains:

```
{x[t], u[t]}
```

The mapping class changes.

This is the canonical M1 construction.

---

## 16. Why the Canonical Construction Is Clean

The canonical construction provides:

- observable inputs;
- observable outputs;
- no required hidden variable;
- deterministic dynamics;
- explicit parameter domains;
- explicit mapping families;
- identifiable target mappings;
- mathematically tractable expressibility;
- direct separation from P1;
- direct separation from R1.

It therefore provides the first controlled M1 benchmark rather than attempting to cover all possible model-family failures.

---

## 17. Domain-Richness Requirement

The experimental protocol must expose sufficient variation.

A bad protocol could make an M1 mapping appear affine.

Example:

```
x[t+1] = x[t]u[t]
```

with:

```
u[t] = 1
```

reduces to:

```
x[t+1] = x[t]
```

which is representable by M0.

Therefore M1 construction must include sufficiently diverse:

- state values;
- action values;
- initial conditions;
- trajectories;
- intervention values.

The evaluator must independently verify that the protocol separates the intended mapping classes.

---

## 18. Canonical Secondary M1 Families

The following are valid future extensions but are not required for the canonical first benchmark.

### 18.1 Temporal M1

If `R₀` already contains:

```
x[t], x[t-1], u[t], u[t-1]
```

then:

`M₀`:
```
x[t+1] = a·x[t] + b·u[t] + c
```

may be compared with:

`M₁`:
```
x[t+1] =
a·x[t]
+ b·x[t-1]
+ c·u[t]
+ d·u[t-1]
+ e
```

No new temporal information may be introduced by M1.

### 18.2 Relational M1

If `R₀` already contains entity states and relations, M1 may introduce richer mappings over those existing relations.

These variants remain deferred until the canonical functional M1 is validated.

---

## 19. No Arbitrary Model Expansion

A model family cannot be constructed after observing the target mapping solely to make it fit.

**Forbidden:**

```
discover f*
    ↓
invent M₁ specifically for f*
    ↓
declare M1
```

**Required:**

```
freeze model-family ladder
    ↓
construct conditions
    ↓
evaluate UNKNOWN
```

The model-family ladder must be independently justified.

---

## 20. Model-Family Ladder

The benchmark should use a finite predefined ladder where appropriate.

Example:

```
M₀ = affine
M₁ = quadratic
M₂ = cubic
```

The ladder is frozen before evaluation.

UNKNOWN cannot create an unlimited sequence:

```
M₀ → M₁ → M₂ → M₃ → ...
```

without an explicit benchmark allowance.

---

## 21. Model Escalation Budget

Each experiment should declare:

- `max_model_family_changes`

and:

- `allowed_model_family_ladder`

If the permitted richer family fails, UNKNOWN may terminate as:

> **UNCERTAIN**

rather than inventing increasingly expressive models indefinitely.

---

## 22. Minimal Sufficient Model Family

When model families are meaningfully nested:

```
F₀ ⊂ F₁ ⊂ F₂
```

the benchmark should record the smallest predefined family known to be sufficient.

Example:

```
F₀ = degree ≤ 1
F₁ = degree ≤ 2
F₂ = degree ≤ 3
```

If the target is quadratic:

```
F₀ ✗
F₁ ✓
F₂ ✓
```

the required family level is `F₁`.

This is a parsimony control, not a claim that smaller models are universally better.

---

## 23. M1/N1 Boundary

M1 requires an identifiable target mapping.

If multiple materially different mappings remain compatible with every permitted public experiment, the condition is N1 rather than M1.

Therefore:

**M1:**
```
target mapping identifiable
+
M₀ insufficient
+
M₁ sufficient
```

**N1:**
```
target mapping itself remains materially ambiguous
```

---

## 24. M1/R1 Boundary

M1 requires the baseline representation to preserve the relevant distinction.

For M1:

```
R₀(H₁) ≠ R₀(H₂)
```
when the relevant outcomes differ.

For an R1 witness:

```
R₀(H₁) = R₀(H₂)
```
while:
```
Y(H₁) ≠ Y(H₂)
```

The representation collision demonstrates information loss.

Therefore:

> A model-family upgrade cannot repair a genuine representation collision.

---

## 25. M1/P1 Boundary

**P1:**

```
∃ θ* ∈ Θ₀
```
such that:
```
M₀(R₀(H); θ*) = f*(H)
```

**M1:**

```
∀ θ ∈ Θ₀
M₀(R₀(H); θ) ≠ f*(H)
```
while:
```
∃ θ₁ ∈ Θ₁
M₁(R₀(H); θ₁) = f*(H)
```

This distinction must be established structurally before final evaluation.

---

## 26. M1/X1 Boundary

Canonical M1 is deterministic:

```
noise = 0
```

Stochastic variation is deferred until X1 is independently controlled.

This prevents model-family failure from being confused with irreducible stochastic error.

---

## 27. M1 Failure and Recovery Protocol

The canonical experimental sequence is:

1. Initialize R₀ + M₀.
2. Collect public evidence.
3. Detect prediction failure.
4. Test parameter explanations.
5. Evaluate M₀ expressibility.
6. Form an M1 hypothesis.
7. Select a discriminative experiment.
8. Run an action or intervention.
9. Observe the public outcome.
10. Evaluate predefined M₁.
11. Keep R₀ fixed.
12. Validate on held-out observations.
13. Validate on held-out interventions where applicable.
14. Validate across permitted contexts.
15. Compare competing explanations.
16. Apply stopping rules.
17. ACCEPT, REJECT, or remain UNCERTAIN.

Failure detection alone never establishes M1.

---

## 28. Parameter-Only Recovery Test

Before model-family expansion, UNKNOWN should determine whether the current model family can recover through parameter revision.

If a valid parameterization exists and generalizes: **P1**

If no valid parameterization exists and the mapping is structurally outside F₀: **M1 candidate**

The benchmark should not require a particular parameter-estimation algorithm.

---

## 29. Discriminative Experiment Selection

When competing model families make different predictions, UNKNOWN may choose an informative experiment.

Conceptually:

```
choose experiment maximizing disagreement(M₀, M₁)
```

subject to:

```
intervention_budget
```

and the declared public protocol.

The environment returns consequences only.

It never returns:

- the correct model;
- the model-family label;
- the reason the intervention was informative.

---

## 30. Intervention Evidence

Interventions are evidence for model-family discrimination.

For competing predictions:

```
M₀ → prediction A
M₁ → prediction B
```

an intervention may produce:

```
A ≠ B
```

The observed consequence then updates the evidence.

Intervention evidence does not by itself prove that a new representation is required.

---

## 31. Held-Out Validation

M1 cannot be established from fitting evidence alone.

Required validation includes, where applicable:

- held-out states;
- held-out actions;
- held-out initial conditions;
- held-out interventions;
- held-out configurations;
- unseen contexts.

Expected canonical result:

```
R₀ + M₀ → fail
R₀ + M₁ → succeed
```

on evidence not used to construct the M1 hypothesis.

---

## 32. Representation-Extension Negative Control

A valid M1 condition should not require a representation extension.

A recovery ladder may therefore test:

```
R₀ + M₀       → fail
R₀ + M₁       → succeed
```

while a representation extension is unnecessary.

If:

```
R₁ + M₀
```

is the only successful route, the condition must be reviewed for possible R1 construction.

---

## 33. Cross-Context Validation

Where the same target mapping is intended to remain valid across contexts, M1 should be evaluated on unseen contexts.

This tests whether M1 recovered a reusable mapping rather than memorizing a local distribution.

Transfer is evidence, not the definition of M1.

---

## 34. No Single-Score M1 Evaluation

The evaluator should record separate dimensions:

- failure detection;
- parameter discipline;
- M0 falsification;
- model-family selection;
- same-R₀ compliance;
- held-out prediction;
- intervention prediction;
- transfer;
- parsimony;
- uncertainty calibration.

No single aggregate score should replace these dimensions.

---

## 35. Acceptance States

### ACCEPT

M1 may be accepted when:

- R₀ is sufficient;
- M₀ is structurally insufficient;
- parameter-only recovery is insufficient;
- M₁ is predefined;
- M₁ is expressively sufficient;
- M₁ uses unchanged R₀;
- target mapping is identifiable;
- held-out validation succeeds;
- required intervention validation succeeds where applicable;
- no leakage is detected;
- reproducibility requirements pass.

### REJECT

M1 should be rejected when:

- M₀ actually contains the target mapping;
- parameter revision explains the failure;
- M₁ uses new representation information;
- M₁ was target-conditioned after seeing the failure;
- apparent improvement is due to leakage;
- target mapping is not identifiable.

### UNCERTAIN

UNKNOWN should remain uncertain when:

- evidence cannot distinguish competing explanations;
- intervention budget is exhausted without discrimination;
- the target mapping is non-identifiable;
- model-family expressibility cannot be established under the declared protocol;
- stochastic effects cannot yet be separated.

---

## 36. Public / Private Boundary

UNKNOWN may receive:

- public observations;
- actions;
- action outcomes;
- intervention outcomes;
- public timestamps or step indices where specified;
- its own predictions;
- its own hypotheses;
- its own uncertainty.

UNKNOWN must not receive:

- condition labels;
- M1 labels;
- R1 labels;
- P1 labels;
- M₀/M₁ ground-truth status;
- true parameters;
- evaluator diagnoses;
- hidden world state;
- expressibility certificates;
- private benchmark annotations.

The evaluator retains these privately.

---

## 37. Anti-Cheating Controls

M1 construction must control:

- metadata leakage;
- identity leakage;
- timing leakage;
- distributional shortcuts;
- intervention availability leakage;
- initialization leakage;
- evaluator leakage;
- raw-observation bypass;
- model-family naming leakage;
- candidate-family contamination;
- target-conditioned family construction.

---

## 38. Reproducibility

M1 experiments inherit the D.4 reproducibility contract.

Each experiment should record:

```
experiment_id
condition_id
scenario_id
trial_id
seed hierarchy
configuration_id
initial state
action sequence
intervention sequence
model-family configuration
evaluation configuration
```

The evaluator retains ground-truth information privately.

UNKNOWN does not receive hidden seed or condition metadata unless explicitly included in the public contract.

---

## 39. Canonical M1 Control Matrix

| Condition | R₀ | M₀ | Parameters | Expected recovery |
|---|---|---|---|---|
| R0 | sufficient | sufficient | correct | baseline success |
| P1 | sufficient | sufficient | wrong | parameter revision |
| M1 | sufficient | insufficient | valid | model-family revision |
| R1 | insufficient | insufficient | valid | representation extension |
| N1 | ambiguous | ambiguous | ambiguous | uncertainty |
| X1 | sufficient | sufficient | valid | stochastic handling |

The matrix is a conceptual control structure and does not replace condition-specific evaluator records.

---

## 40. Scientific Interpretation

A successful M1 diagnosis means:

> The available representation already contained the required information, but the current mapping class could not express the target relationship.

It does not mean:

- UNKNOWN discovered a new concept;
- UNKNOWN discovered a new representation;
- M1 is universally superior;
- a larger model is always preferable.

M1 establishes only the controlled distinction between representation sufficiency and model-family sufficiency.

---

## 41. Scientific Risks

Remaining risks include:

- accidental representation expansion;
- insufficient experimental domain richness;
- hidden parameter confounding;
- empirical failure being mistaken for expressibility failure;
- target-conditioned model-family construction;
- finite-domain memorization;
- excessive model escalation;
- benchmark-specific overfitting;
- implementation-specific artifacts;
- insufficient held-out validation.

These must be controlled before executable implementation.

---

## 42. Research Decision

S0.5-D.5.3.3 is conceptually accepted.

The M1 condition is formally separated from P1 and R1:

```
P1 = parameter insufficiency
M1 = mapping-family insufficiency
R1 = representation insufficiency
```

The canonical benchmark uses:

```
Typed Functional Dynamics
M₀ = bounded affine mapping
M₁ = bounded interaction/quadratic mapping
```

The canonical condition is deterministic, identifiable, publicly recoverable, and uses an unchanged R₀.

The benchmark includes:

- expressibility boundaries;
- constructive witnesses;
- parameter-only controls;
- same-R₀ invariants;
- intervention discrimination;
- held-out validation;
- cross-context validation;
- model-family stopping;
- parsimony;
- uncertainty outcomes;
- evaluator isolation;
- reproducibility.

No implementation should begin until this research contract is incorporated into the executable benchmark design.
