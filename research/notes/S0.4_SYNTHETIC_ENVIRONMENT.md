# Project UNKNOWN — S0.4 Synthetic Environment Specification

**Status:** Working scientific specification
**Sprint:** Sprint 0 — S0.4
**Date:** 2026-09-23
**Purpose:** Define the first synthetic environment family used to test whether UNKNOWN can distinguish parameter failure, model-family failure, representation-level inadequacy, and representation-language insufficiency.

---

# 1. Purpose

The first Project UNKNOWN environment must function as a controlled scientific benchmark.

It must not merely demonstrate that a system can improve prediction.

It must provide controlled cases in which:

1. parameters are inadequate;
2. the selected model family is inadequate;
3. the current representation is inadequate;
4. the representation-extension language is inadequate.

The hidden cause of each condition must remain unavailable to UNKNOWN.

The environment is therefore designed as a paired causal-diagnostic benchmark rather than a single prediction dataset.

---

# 2. Environment Family

The first environment family is a relational dynamical world.

The world contains multiple entities whose observable attributes and relationships evolve over time.

The environment is intentionally non-visual for the initial benchmark.

This removes unnecessary complexity from the first scientific test while preserving the central representation problem.

A later benchmark may introduce visual observations.

---

# 3. Environment Formalization

The environment is defined as:

$$
E=(S,A,O,T)
$$

where:

* \(S\) = hidden environment state;
* \(A\) = available actions/interventions;
* \(O\) = observation process;
* \(T\) = transition mechanism.

The environment produces trajectories:

$$
\tau=(s_0,o_0,a_0,s_1,o_1,\ldots)
$$

UNKNOWN receives permitted observations and actions but not hidden state.

---

# 4. Hidden State

The hidden state contains:

* entity identities;
* entity attributes;
* entity positions;
* entity velocities;
* latent relational structure;
* environment parameters;
* transition state;
* task-relevant hidden variables where applicable.

Hidden state exists for benchmark construction and evaluation.

It is never directly exposed to UNKNOWN during discovery.

---

# 5. Entities

Each environment instance contains a bounded number of entities.

An entity may have:

* identifier;
* type;
* position;
* velocity;
* scalar attributes;
* discrete attributes.

The exact dimensionality is configuration-controlled.

Entity identities are not assumed to carry semantic meaning.

The benchmark must include randomized identities where necessary to prevent memorization.

---

# 6. Observable State

The observation interface exposes a declared subset of environment information.

An observation may include:

```text
entity_id
entity_type
position
velocity
observable_attributes
permitted_relations
timestamp
```

The observation interface is controlled by configuration.

Hidden state must never be silently exposed through serialization, metadata, filenames, logging, or API responses.

---

# 7. Observation History

UNKNOWN may receive a sequence:

$$
o_{\leq t}=(o_0,\ldots,o_t)
$$

The initial representation operates over this permitted history.

This allows temporal representations where necessary.

The system must distinguish:

```text
current observation
```

from:

```text
derived temporal representation
```

---

# 8. Actions

The environment supports controlled actions.

An action may affect:

* entity position;
* entity velocity;
* environment parameters;
* interaction conditions.

Actions are explicitly typed.

The environment must reject invalid actions rather than silently changing their meaning.

---

# 9. Interventions

Interventions are controlled changes to specified environment variables.

An intervention must record:

```text
intervention_id
target
previous_state
intervention_value
time
resulting_observation
```

The intervention mechanism must distinguish ordinary trajectory evolution from externally imposed intervention.

---

# 10. Transition Dynamics

The initial environment uses deterministic or seeded stochastic transition dynamics.

A transition has the conceptual form:

$$
s_{t+1}=T(s_t,a_t;\theta_E,\epsilon_t)
$$

where:

* \(\theta_E\) = environment parameters;
* \(\epsilon_t\) = controlled stochasticity.

All stochasticity must be seedable.

The environment must support deterministic replay from:

```text
environment configuration
+
seed
+
initial state
+
action sequence
```

---

# 11. Relational Structure

The benchmark's central representation challenge is relational.

Relationships may include:

* distance;
* relative position;
* ordering;
* proximity;
* persistence;
* change;
* temporal ordering.

Some relationships are directly observable.

Others may need to be constructed from permitted primitives.

The environment must distinguish primitive relational measurements from higher-level candidate concepts.

---

# 12. Candidate Concept Example

A candidate concept may take the form:

$$
near(A,B)
=
distance(A,B)<\delta
$$

where:

* `distance` is an allowed primitive;
* `delta` is a bounded learned or discovered threshold;
* `near` is the candidate reusable abstraction.

The benchmark must not provide the name `near` to UNKNOWN.

The candidate may instead be represented structurally.

For example:

```text
distance(A,B) < threshold
```

The scientific question is whether UNKNOWN can construct and validate such an abstraction from systematic evidence.

---

# 13. Initial Representation

The initial representation must deliberately expose enough information for some tasks while withholding specific distinctions required by others.

Example:

$$
R_0(o_{\leq t})
$$

may contain:

* object attributes;
* positions;
* velocities;
* pairwise distances;
* temporal differences.

But the representation may not initially contain:

* thresholded relational predicates;
* persistent relational states;
* composed temporal relations.

These can be candidates for representation extension.

The exact initial representation must be frozen before the final benchmark.

---

# 14. Representation Extension

A candidate extension has the form:

$$
R'=R_0\oplus C
$$

where \(C\) belongs to the predefined extension language.

Candidate expressions must be constructed from permitted primitives.

The environment must not provide a hidden API such as:

```text
get_true_concept()
```

or any equivalent mechanism.

---

# 15. Environment Conditions

The environment family must generate controlled failure conditions.

## 15.1 Parameter Failure

The representation contains the required information.

The selected model family can solve the task.

The initial parameter state is intentionally inadequate.

Expected resolution:

```text
parameter optimization
```

---

## 15.2 Model-Family Failure

The representation contains the required information.

The initial model family cannot express the required mapping.

A predefined stronger model family can solve the task using the same representation.

Expected resolution:

```text
model-family expansion
```

---

## 15.3 Representation Failure

The required distinction is absent from the current representation.

All predefined model families operating on the current representation fail the adequacy criterion.

An admissible representation extension can express the missing distinction.

Expected resolution:

```text
representation extension
```

---

## 15.4 Language Insufficiency

The required distinction is outside the current extension language.

No permitted candidate can express the required structure.

Expected resolution:

```text
report language limitation
```

The system must not fabricate a successful concept.

---

# 16. Paired Counterfactual Benchmark

The most important environment design is the paired comparison.

## Pair A — Model-Family Limitation

The task-relevant information is available in \(R_0\).

A weak model family fails.

A stronger predefined model family succeeds.

Expected diagnosis:

```text
MODEL_FAMILY_FAILURE
```

No representation extension should be necessary.

---

## Pair B — Representation Limitation

The task-relevant distinction is unavailable in \(R_0\).

All predefined model families operating on \(R_0\) fail.

A valid candidate extension \(C\) makes the task solvable.

Expected diagnosis:

```text
REPRESENTATION_FAILURE
```

The environment must be constructed so that Pair A and Pair B are difficult to distinguish from superficial prediction errors alone.

---

# 17. Encoded Information Condition

A third condition should test whether information exists but requires a more expressive transformation.

For example, the observation may contain:

$$
x
$$

while the target depends on:

$$
x^2
$$

or another permitted nonlinear transformation.

The initial model family may fail to express the required transformation.

A stronger model family should succeed without changing the representation.

This condition protects against falsely classifying difficult decoding as representation failure.

---

# 18. Removed Information Condition

A separate condition removes the relevant information from the representation.

The hidden environment may contain the required variable, but the observation interface does not expose it.

No model operating only on the resulting representation should be expected to reconstruct information that is genuinely absent.

This condition forms an important diagnostic boundary.

---

# 19. Decoy Structure

The environment should contain correlations that are useful during discovery but invalid under independent evaluation.

Examples include:

* identity-correlated shortcuts;
* initial-condition correlations;
* surface attributes correlated with the target;
* trajectory-specific regularities.

These decoys are intentional.

They test whether UNKNOWN discovers reusable structure or merely exploits accidental correlations.

---

# 20. Transfer Variation

Transfer environments vary controlled nuisance dimensions.

Possible dimensions include:

* entity identities;
* initial positions;
* velocity distributions;
* irrelevant attributes;
* environment parameter values;
* number of entities;
* trajectory length.

The underlying candidate relation, when applicable, should remain stable across the intended transfer family.

This allows evaluation of representation reuse.

---

# 21. Hidden Ground Truth

The environment generator may know:

* true hidden state;
* true transition mechanism;
* intended relational structure;
* benchmark condition;
* true causal relationships.

UNKNOWN must not receive these values.

Ground truth is stored separately from discovery artifacts.

Ground truth may be used after evaluation to classify:

* actual failure condition;
* exact candidate recovery;
* equivalent candidate recovery;
* false discovery;
* benchmark behavior.

---

# 22. Ground-Truth Storage

Ground truth must never be embedded in ordinary observation payloads.

The implementation should maintain separate conceptual layers:

```text
environment/
    public/
    hidden/
    evaluation/
```

The public layer is accessible to UNKNOWN.

The hidden layer is accessible only to benchmark evaluation.

The evaluation layer contains post-run analysis artifacts.

Runtime code must enforce this separation.

---

# 23. Randomization

Each benchmark instance should support controlled randomization.

Randomization may affect:

* entity identities;
* initial state;
* irrelevant attributes;
* trajectory order;
* environment parameters.

Randomization must never change the intended failure classification unless the benchmark configuration explicitly defines a new condition.

---

# 24. Seeds

Every experiment receives a seed.

The seed controls all benchmark randomness.

At minimum, records must include:

```text
global_seed
environment_seed
initial_state_seed
intervention_seed
```

If independent random streams are used, each stream must be recorded.

---

# 25. Deterministic Replay

Given:

```text
configuration
seed
initial state
action sequence
```

the environment must reproduce the same trajectory within the declared numerical tolerance.

Replay tests are mandatory.

---

# 26. Numerical Stability

The environment must define:

* numeric precision;
* tolerance rules;
* comparison semantics;
* overflow behavior;
* invalid-state handling.

Numerical differences must not be confused with scientific differences.

---

# 27. Episode Definition

An episode consists of:

```text
initialization
    ↓
observation
    ↓
zero or more actions
    ↓
state transitions
    ↓
terminal condition
```

Each episode receives a unique identifier.

Episode metadata must include the environment configuration version and seed.

---

# 28. Task Definition

A benchmark task is a formal prediction/intervention problem defined over environment trajectories.

A task specifies:

* input observation history;
* available actions;
* prediction target;
* evaluation metric;
* adequacy threshold;
* allowed model families;
* representation constraints.

Tasks must not expose their hidden failure category.

---

# 29. Adequacy Threshold

Each task declares an adequacy threshold:

$$
\tau
$$

The threshold is selected before final evaluation.

A model is adequate when:

$$
Score(M,R)\geq\tau
$$

according to the task-specific metric.

Threshold selection must use development data or prior benchmark calibration, not final test performance.

---

# 30. Model-Family Controls

The environment specification does not prescribe one universal model family.

Instead, each task declares a bounded set of admissible families.

Examples may include:

```text
linear
polynomial
tree-based
small neural network
sequence model
```

The exact initial families are finalized during S0.6.

UNKNOWN must not expand the family set after observing final test results.

---

# 31. Complexity Budget

Candidate representations receive a complexity cost.

Possible components include:

* number of primitives;
* expression depth;
* number of operators;
* number of learned constants;
* temporal window size.

The final complexity metric is frozen before candidate comparison.

---

# 32. Candidate Generation Boundary

The environment must provide enough structure for candidate discovery without revealing the answer.

Candidate generation may use:

* residual analysis;
* error clustering;
* temporal segmentation;
* relation analysis;
* permitted symbolic composition.

Candidate generation may not use:

* hidden state;
* benchmark labels;
* hidden concept names;
* final test outcomes;
* human-provided hints.

---

# 33. Intervention Families

Interventions should test whether a candidate captures a meaningful relationship rather than merely correlating with observations.

Potential intervention families include:

### Position intervention

Change an entity's position while controlling other variables.

### Attribute intervention

Change an irrelevant or task-relevant attribute independently.

### Relation intervention

Move entities relative to each other.

### Temporal intervention

Alter a sequence or persistence condition.

Each intervention family must have declared validity constraints.

---

# 34. Falsification Opportunities

Each intended candidate concept must have environments where its hypothesis could fail.

For example, if a candidate implies:

$$
distance(A,B)<\delta
\Rightarrow
Y=1
$$

the benchmark should contain cases near and beyond the threshold.

The benchmark must not only present easy confirming examples.

---

# 35. Transfer Contract

A candidate representation discovered in environment \(E_d\) must be evaluated in:

$$
E_{transfer}
$$

where selected nuisance factors differ.

Transfer environments must preserve the intended structural relation when the candidate is supposed to be reusable.

A candidate that succeeds only because of discovery-environment artifacts should fail independent transfer.

---

# 36. Anti-Memorization Design

The environment should prevent simple memorization through:

* randomized entity IDs;
* randomized initial states;
* varied trajectories;
* varied nuisance attributes;
* independent transfer environments;
* withheld combinations.

The benchmark should measure whether the candidate represents reusable structure.

---

# 37. Observation Leakage Audit

Before experiments begin, inspect every public observation field.

The audit must verify that no field accidentally reveals:

* benchmark condition;
* hidden state;
* intended concept;
* evaluation split;
* target construction;
* ground-truth label.

This audit is mandatory.

---

# 38. API Boundary

The environment runtime should expose only the permitted public interface to UNKNOWN.

Conceptually:

```text
reset(config, seed)
observe()
step(action)
intervene(intervention)
is_terminal()
episode_metadata()
```

Evaluation-only functionality must exist outside this interface.

---

# 39. Environment Versioning

Every environment configuration receives a version identifier.

Changes to:

* transition dynamics;
* observation fields;
* action semantics;
* candidate language;
* task definition;
* thresholds

must create a new version.

Results must reference the exact environment version.

---

# 40. Configuration Separation

Environment configuration should be separated from implementation code.

At minimum, distinguish:

```text
environment definition
task definition
observation configuration
model configuration
evaluation configuration
random seed
```

This allows controlled experiments without modifying source code.

---

# 41. Initial Benchmark Scale

The first implementation should remain computationally bounded.

Initial experiments should support:

* small entity counts;
* short episodes;
* deterministic replay;
* multiple random seeds;
* multiple environment instances;
* multiple failure conditions.

Scale may increase only after scientific correctness is established.

---

# 42. Scientific Priority

The initial benchmark prioritizes:

1. causal diagnostic clarity;
2. representation separation;
3. reproducibility;
4. anti-leakage guarantees;
5. falsifiability;
6. independent validation.

Large-scale performance is secondary during the first environment implementation.

---

# 43. Required Environment Tests

Before UNKNOWN is allowed to run experiments, the environment must pass tests for:

* deterministic replay;
* observation isolation;
* hidden-state isolation;
* action validation;
* intervention correctness;
* seed reproducibility;
* configuration versioning;
* failure-condition generation;
* transfer generation;
* no hidden-label leakage.

---

# 44. Required Evidence

S0.4 evidence must eventually contain:

* environment configuration;
* public API description;
* hidden-state schema;
* observation schema;
* action schema;
* intervention schema;
* failure-condition definitions;
* transfer definitions;
* randomization strategy;
* replay verification;
* leakage audit.

---

# 45. S0.4 Boundary

S0.4 defines the synthetic world.

It does not yet define:

* the final UNKNOWN discovery algorithm;
* final baseline implementations;
* final statistical analysis;
* production deployment;
* large-scale training.

Those belong to later stages.

---

# 46. Scientific Risk

The primary risk is constructing an environment where the intended distinction is accidentally obvious.

A benchmark is scientifically weak if:

```text
representation failure
```

can be identified directly from metadata, feature names, task names, or trivial missing-field inspection.

The system must instead infer the distinction from observed performance and permitted experiments.

---

# 47. Adversarial Review Requirement

Before S0.4 is considered complete, review the environment against the following questions:

1. Can a strong model solve the alleged representation-failure condition without representation extension?
2. Does the current representation secretly contain the missing distinction?
3. Can a simple decoder recover the intended concept?
4. Does the candidate merely memorize environment identity?
5. Can a decoy candidate pass prediction but fail intervention?
6. Can a decoy candidate pass discovery but fail transfer?
7. Can UNKNOWN access hidden labels indirectly?
8. Can the environment distinguish model-family failure from representation failure?
9. Can another representation express the same behavior without being counted as failure?
10. Does the benchmark accidentally favor UNKNOWN?

Any unresolved positive answer requires environment revision.

---

# 48. S0.4 Definition of Done

S0.4 is complete only when:

* the environment formalization is frozen;
* public and hidden interfaces are separated;
* failure conditions are explicitly constructible;
* paired model/representation cases exist;
* intervention semantics are defined;
* transfer semantics are defined;
* deterministic replay is specified;
* randomization is controlled;
* leakage risks are documented;
* required environment tests are defined;
* adversarial review is completed;
* all changes are documented;
* the sprint evidence is recorded;
* Git commit and push are completed.

---
