# S0.5-D.5.3.3 — M1 Model-Family Failure Evidence

## Status

**Research/design evidence — ready for closure**

---

## 1. Objective

D.5.3.3 defines the controlled construction of M1 Model-Family Failure.

The purpose is to establish a benchmark condition where:

```text
R₀ is sufficient
M₀ is insufficient
M₁ is sufficient
```

while keeping the representation unchanged.

The scientific distinction is:

```text
P1 → parameters are wrong
M1 → mapping family is insufficient
R1 → representation is insufficient
```

## 2. Research Question

The central question is:

> Can UNKNOWN distinguish failure of a model family from failure of its parameters and from failure of its representation?

A valid M1 benchmark must answer this structurally rather than relying only on predictive score differences.

## 3. Starting Boundary

D.5.3.1 established the model-family boundary.

D.5.3.2 established P1 parameter-failure construction.

D.5.3.3 builds on both.

The current boundary is:

```text
P1:
R₀ ✓
M₀ ✓
θ₀ ✗

M1:
R₀ ✓
M₀ ✗
M₁ ✓

R1:
R₀ ✗
M₀ ✗
M₁ ✗
R₁ ✓
```

## 4. Core Decision

M1 is a model-family failure.

It is **not** defined as:

```text
M₁ performs better than M₀
```

It **is** defined as:

```text
f* ∉ Closure(M₀, R₀)
f* ∈ Closure(M₁, R₀)
```

with identifiable target mapping and unchanged representation.

## 5. Model-Family Semantics

A model family is a predefined class of admissible mappings from representation to outcome.

Model-family identity is based on:

- mapping grammar
- parameter domain
- composition rules
- admissible operations
- resource constraints

It is **not** based solely on:

- software framework
- architecture name
- model size
- parameter count
- optimization algorithm

## 6. Closure Decision

The concept of model-family closure provides the primary distinction.

For M₀:

```text
Closure(M₀, R₀)
```

is the set of mappings that can be expressed from the frozen R₀ representation using M₀.

For M1:

```text
f* ∉ Closure(M₀, R₀)
```

while:

```text
f* ∈ Closure(M₁, R₀)
```

This is the defining structure.

## 7. Why Performance Alone Is Insufficient

An M0 model can fail despite containing the true mapping because of:

- poor initialization
- optimization failure
- finite data
- numerical problems
- implementation errors
- insufficient fitting budget

Therefore:

> Model-family insufficiency must be structurally established independently of a single model-training result.

## 8. Constructive Witness

A valid M1 condition should have an evaluator-side witness showing:

```text
f* ∉ F₀
```

and:

```text
f* ∈ F₁
```

For finite domains, the evaluator can use a witness set:

```text
D = {(r₁,y₁), ..., (rₙ,yₙ)}
```

where no function in F₀ satisfies all required mappings while an allowed function in F₁ does.

This provides an executable validation mechanism.

## 9. Finite-Domain Risk

A finite dataset can be memorized by a sufficiently flexible model.

Therefore M0 and M1 must be frozen function families rather than arbitrary fitting systems.

An unrestricted lookup-table model is not an acceptable canonical M0.

The benchmark requires bounded and typed model-family definitions.

## 10. Canonical World

The canonical world family is:

**Typed Functional Dynamics**

with:

```text
x[t+1] = F*(x[t], u[t])
```

The state, action, and outcome are publicly observable.

The target transition function remains evaluator-private.

## 11. Canonical Representation

The canonical representation includes the publicly relevant information:

- state
- action
- previous_state
- step_index

The exact R₀ contract remains governed by D.5.1.

The canonical M1 construction does not require hidden state.

## 12. Canonical M0

The baseline model family is bounded affine dynamics:

```text
x[t+1] = a·x[t] + b·u[t] + c
```

or its typed vector analogue.

The parameter domain is explicit and frozen.

## 13. Canonical M1

The richer family introduces bounded interaction structure:

```text
x[t+1]
    = a·x[t]
    + b·u[t]
    + c·x[t]u[t]
    + d
```

The public representation does not change.

The mapping class changes.

## 14. Why This Is M1

The canonical construction has:

```text
R₀ sufficient
```

because x[t] and u[t] are public.

It has:

```text
M₀ insufficient
```

because affine mappings cannot represent the required interaction mapping over a sufficiently rich domain.

It has:

```text
M₁ sufficient
```

because the interaction term belongs to M1.

Therefore:

```text
R₀ + M₀ → fail
R₀ + M₁ → succeed
```

## 15. Parameter Boundary

P1 changes only parameter values within M0.

M1 changes the mapping class.

For example:

```text
M₀:
y = ax + b
```

Changing `a` or `b` is P1.

Introducing:

```text
cx²
```

or:

```text
cxu
```

is a model-family change when that structure is outside M0.

## 16. Representation Boundary

If:

```text
R₀ = {x,u}
```

then M1 may not silently replace it with:

```text
R₁ = {x,u,xu}
```

unless that representation component was already within the frozen R₀ closure.

Otherwise the experiment becomes representation expansion rather than pure M1.

## 17. Raw Observation Boundary

M1 implementations must not bypass R₀.

The model receives only the representation defined by the benchmark.

It must not directly access:

- raw hidden observations
- hidden state
- evaluator annotations
- condition labels
- private mechanism identifiers

This prevents model-family expansion from becoming information leakage.

## 18. Domain-Richness Evidence

An M1 world is invalid if the experimental protocol collapses the richer mapping into a simpler one.

Example:

```text
x[t+1] = x[t]u[t]
```

with constant:

```text
u[t] = 1
```

becomes:

```text
x[t+1] = x[t]
```

which is affine.

Therefore the benchmark must vary the public inputs sufficiently to preserve the intended distinction.

## 19. Identifiability

The target mapping must be identifiable under the permitted public protocol.

If multiple materially different mappings remain compatible with all permitted evidence, the condition belongs to N1 rather than M1.

Identifiability is a property of:

- representation
- model family
- public observations
- action/intervention protocol
- experimental domain
- noise assumptions
- horizon

## 20. Deterministic Canonical Control

Canonical M1 uses:

```text
noise = 0
```

and deterministic transitions.

Stochastic variants are deferred.

This keeps:

```text
model-family insufficiency
```

separate from:

```text
stochastic variation
```

## 21. Recovery Ladder

The expected recovery sequence is:

```text
R₀ + M₀
    ↓
prediction failure

R₀ + M₀ + parameter revision
    ↓
still fails

R₀ + M₁
    ↓
recovery

held-out R₀ + M₁
    ↓
generalization

intervention + M₁
    ↓
interventional validation
```

The key evidence is not merely that M1 succeeds.

It is that M0 remains insufficient after parameter revision while M1 succeeds without changing R0.

## 22. Parameter-Only Negative Control

A P1 control must be run alongside M1 conditions.

The P1 control demonstrates that parameter revision can solve some prediction failures.

This prevents UNKNOWN from treating every failure as model-family failure.

Expected:

```text
P1:
M₀ + corrected θ → success

M1:
M₀ + any valid θ → failure
M₁ → success
```

## 23. Representation Negative Control

An R1 control demonstrates a separate case where model-family expansion cannot solve the problem because R0 has lost relevant information.

Expected:

```text
R1:
R₀ + M₀ → failure
R₀ + M₁ → failure
R₁ + appropriate model → success
```

This prevents model-family expansion from being treated as a universal remedy.

## 24. Intervention Evidence

Interventions can separate competing M0 and M1 predictions.

For example:

```text
M₀ → prediction A
M₁ → prediction B
```

An informative intervention can produce different observable outcomes.

The result updates evidence about the competing models.

The intervention does not reveal the correct model directly.

## 25. Active and Passive M1

**Passive M1**

The ordinary observation/action stream provides enough information to identify the mapping.

**Active M1**

UNKNOWN may choose actions or interventions specifically to distinguish competing model families.

The underlying ground truth remains M1.

Active experimental design is an inference strategy, not a change in condition type.

## 26. Held-Out Evidence

Training evidence is insufficient.

M1 should be tested using held-out:

- states
- actions
- initial conditions
- configurations
- interventions
- contexts

Where transfer is part of the experiment, the target mapping should remain fixed while superficial context changes.

## 27. Same-R₀ Requirement

A valid M1 recovery has:

```text
R₀ + M₀ → failure
R₀ + M₁ → success
```

not:

```text
R₀ + M₀ → failure
R₁ + M₁ → success
```

The second result confounds model-family and representation changes.

## 28. Model Escalation

The benchmark must define:

- allowed_model_family_ladder
- max_model_family_changes

UNKNOWN must not escalate indefinitely.

If the permitted family fails, the valid result may be:

```text
UNCERTAIN
```

rather than unlimited model growth.

## 29. Parsimony

If:

```text
F₀ ⊂ F₁ ⊂ F₂
```

and F1 is sufficient, the benchmark records F1 as the minimal predefined sufficient family.

Complexity is measured separately from predictive success.

This prevents excessive expressivity from being rewarded automatically.

## 30. Falsification Before Acceptance

The protocol prioritizes falsification.

UNKNOWN should attempt to determine:

> Can M₀ explain the evidence?

before concluding:

> M₀ is inadequate.

Then it should seek evidence that distinguishes:

```text
M₀
vs
M₁
```

Only after this should M1 be accepted.

## 31. Acceptance Evidence

Strong M1 evidence consists of:

- R₀ sufficiency
- identifiable target mapping
- M0 expressibility failure
- parameter-only recovery failure
- predefined M1 expressibility
- unchanged R0
- held-out M1 recovery
- intervention validation where applicable
- cross-context validation where applicable
- no leakage
- reproducibility

## 32. Rejection Evidence

M1 should be rejected if:

- M0 can represent the target mapping
- parameter revision solves the failure
- the target mapping is not identifiable
- M1 requires new representation information
- M1 accesses raw observations outside R0
- M1 was invented after observing the target
- apparent recovery disappears on held-out data
- recovery is explained by leakage

## 33. Uncertainty Evidence

UNKNOWN should remain uncertain if:

- multiple mappings remain compatible with evidence
- the experiment cannot distinguish M0 and M1
- intervention budget is exhausted
- model-family expressibility cannot be established
- stochastic effects remain unresolved
- benchmark conditions are contaminated

Uncertainty is a valid scientific outcome.

## 34. Anti-Leakage Evidence

The benchmark must verify absence of:

- condition metadata
- model-family labels
- parameter truth
- evaluator diagnosis
- hidden state
- semantic entity names
- special timing signatures
- special intervention availability
- raw-observation bypass

## 35. Reproducibility Evidence

Experiments inherit the D.4 reproducibility contract.

The evaluator records:

- experiment_id
- condition_id
- scenario_id
- trial_id
- seed hierarchy
- configuration_id
- initial state
- action sequence
- intervention sequence
- model-family configuration
- evaluation configuration

Repeated runs under the same declared configuration should reproduce expected deterministic behavior.

## 36. Scientific Risks

The major risks are:

- treating optimization failure as M1
- insufficient public-domain variation
- hidden representation expansion
- raw-observation bypass
- target-conditioned model construction
- finite-data memorization
- unlimited model escalation
- confusing N1 with M1
- confusing X1 with M1
- benchmark-specific overfitting

Each is explicitly controlled by the D.5.3.3 contract.

## 37. Scientific Review

The D.5.3.3 design was reviewed against:

- P1 parameter failure
- R1 representation failure
- N1 non-identifiability
- X1 stochastic variation
- representation leakage
- model-family leakage
- target-conditioned model construction
- finite-domain memorization
- excessive model complexity
- unlimited escalation
- intervention confounding
- held-out validation

The conceptual boundaries remain coherent.

## 38. Research Decision

D.5.3.3 is ready for artifact closure.

The final distinction is:

```text
P1 → change parameterization
M1 → change mapping class
R1 → change representation
N1 → insufficient evidence
X1 → stochastic explanation
```

The canonical M1 benchmark is:

```text
Typed Functional Dynamics
R₀ = public state/action representation
M₀ = bounded affine mapping
M₁ = bounded interaction/quadratic mapping
```

The target mapping is identifiable and evaluator-private.

The benchmark preserves the public/private boundary and requires held-out validation.
